## Ground rules

- Each item lands as its own commit, with before/after numbers in the commit message
  and in this file.
- Soundness gate before every commit: whole `pytest -q` run with
  `env -u LD_LIBRARY_PATH` (includes `tests/bench`), and the QF_BV fuzzer
  (`tests/formal/test_fuzz_cross_check.py`, `FUZZ_N` raised) for items 1–3, which touch
  the encoder and the model. Zero disagreements is the bar.
- Timing: median of 3 runs, same machine, built from a ref (`builds.build_tag`), not by
  copying a binary. The CLI loads `libdv_solve.so` from its build dir.
- All build and timing output goes to log files.

## Item 1: `dvs_aig_cnf` visited bitmap (25% of `vlsat3_a67`)

**Problem.** `dvs_aig_cnf_encode` (`src/c/dvs_aig_cnf.c:275`) frees the visited bitmap
at the start of every top-level flatten. `ensure_bitmap` (:48) then regrows it and
memsets it to zero. Cost is O(top-level asserts × AIG nodes). `a67` has many top-level
asserts over a large AIG, so memset is 25% of the run.

**Bug in the same lines.** `e->visited_cap = 0` is set *before*
`xfree(e->alloc, e->visited, e->visited_cap)`, so the free is passed size 0. This makes
the `dvs_alloc_t` byte accounting wrong (it is not a memory-safety issue). Fix it first,
as a separate commit.

**Fix.**
1. Keep the bitmap between flatten passes.
2. Record each bit set during the pass (the `bit_idx` values, or the node ids pushed),
   and clear only those bits at the end of the pass. An alternative is a per-node epoch
   stamp (`uint32_t` per id, pass counter), which needs no clear at all; pick whichever
   is smaller in memory for large AIGs (the bitmap is 2 bits/node, the epoch 4 bytes/node).
3. Check for other per-assert full clears in `dvs_aig_cnf.c` and `encode_subtree`.

**Tests.** An encoder unit test that asserts a shared subtree in both polarities across
several top-level calls (the soundness note at :290 says +id and −id must not dedup each
other). Allocator-tracker test showing the bytes balance after destroy.

**Target.** The memset share in `a67` drops from 25% to near 0; expect around 1.3× on
`a67`. Check `a57` and the easy band for regressions.

Log: done 2026-10-17.
- 3f5eedc: the `xfree` size fix, with a counting-allocator test in `test_dvs_aig_cnf`.
  Before the fix it reported 230496 bytes allocated and 207008 released.
- The bitmap fix: the visited bitmap now persists between passes. A `touched` list
  records each bit a pass sets, and the pass clears only those bits. The leaves buffer
  is reused too. I chose the touched list over epoch stamps because it costs 4 bytes
  per node visited in the pass, not 4 bytes per AIG node. `encode_subtree`'s
  `encoded` bitmap was already persistent, so there were no other per-assert clears.
- `test_dvs_aig_cnf` also checks that a second pass over the same AND asserts its
  leaves again, and that `a ∧ b` followed by `¬a ∧ c` is UNSAT.
- a67: libc mem/str share 19.8% → 3.5%. Time 7.141 → 5.381 s (median of 5, interleaved
  builds; the machine was loaded, at load average ~13). a57 1.286 → 1.256 s and the
  easy band 3.07 → 3.11 s are noise.

## Item 2: AIG unique table (7–9% in easy band and `a67`)

**Problem.** `intern_and` (`src/c/dvs_aig.c:111`) uses chained buckets: a bucket
array of node indices, with the chain link stored in each node (`next_in_bucket`).
Each probe step is a dependent load into the node array, which is a cache miss on large
AIGs.

**Fix options, in order of cost.**
1. Measure first: average chain length and the miss rate at the load in the loop.
   Check `bucket_hash` (:81) quality and the load factor (resize happens at 1.0).
   A better mix or a 0.5 load factor may be enough.
2. Open addressing with linear probing over a separate slot array storing
   `(left, right, id)` together (12 bytes per slot, or 16 aligned), so a hit or miss
   is decided without touching `m->nodes`. Drop `next_in_bucket` from the node.
3. Keep the public `dvs_aig_*` API unchanged; nodes are never deleted, so no
   tombstones are needed. Check `dvs_aig` reset/checkpoint paths that rewind
   `nodes_size`: those must also remove entries from the table.

**Tests.** Existing AIG and bitblast tests, the fuzzer, and a hash-consing test asserting
that structurally identical ANDs return the same id across a resize.

**Target.** `dvs_aig_mk_and` self time halved. Overall 3–5% on the easy band and `a67`.

Log: measured 2026-10-17, not landed.
- Before: perf annotate of `dvs_aig_mk_and` in a67 put 35% of its self time in
  `buckets_resize` (the rehash walks each chain through `m->nodes`), 24% in the
  bucket-array load and 20% in the chain-walk compare. `bucket_hash` also ignores the
  literal signs, so all four polarity variants of a pair share one bucket.
- Tried: open addressing with linear probing, `(left, right, id)` slots at a 1/2 load
  factor, a Fibonacci hash of the signed pair, and `next_in_bucket` dropped from the
  node (16 → 12 bytes). Resize fell to ~10% of the function. Half of what is left is
  the one slot miss per lookup, which any random-access table this size pays.
- Result: a67 −0.8% user cycles (26.8G → 26.6G); easy band no change (8.8G both).
  `dvs_aig_mk_and` is still 7.5% of a67.
- A hash-only variant (chained table, signed Fibonacci hash) was no better.
- Not landed: the table costs ~16 bytes more per AND node, for under 1%. The patch is
  not kept. The hash-consing test it came with is committed, because it checks the
  current table: four polarity variants per pair are distinct nodes, and rebuilding
  after many resizes returns the same ids.

## Item 3: `_diversify` in the Verilator loop (37.5% of the Verilator run)

**What the profile shows.** The hottest lines are the flip loop and `_prop_cone`
(`dvs_bbsolver.c:2187`, :2063–2065), not only the per-call setup. So caching the setup
(L/R arrays, fanout CSR, `areq`) helps, but it may not be the main lever. Split the
cost before choosing.

**Step 3a: why this path runs at all.** [[verilator-cdcl-routing]] says
`--mode=verilator` samples through CDCL. Commit 035f066 (`dvs_bbsolver_sample`) added
a sampling path that calls `_diversify`. Find which benches in the transcript reach
bitblast, and whether that is intended (API/SMT2 parity rule: only Verilator mode is
allowed to differ). If the routing is unintended, fixing it may remove most of the cost.
Record the decision here before optimizing.

**Step 3b: measure the split.** Instrument (or perf-annotate) setup vs flip loop vs
revert: the number of candidate bits, flips attempted, flips rejected, and the average
cone size per flip.

**Step 3c: levers, chosen by 3b.**
- Setup: cache L/R, the fanout CSR and the scratch buffers on `S`, keyed on the AIG
  node count (the AIG is append-only between resets) and rebuilt incrementally or on
  reset. Rebuild `areq` only when the assert set changes. Replace the six
  malloc/calloc/free pairs per call with reused buffers.
- Flip loop: `_prop_cone` uses a binary heap so nodes are evaluated in topological
  order. Since ids are topological, a bucketed or bitset-by-id worklist would avoid the
  log factor. Rejected flips pay for the whole cone and then revert it; precomputing,
  per input, whether its cone reaches any asserted node would let flips with no
  asserted node in the cone be accepted without propagation (the readback still needs
  the values, so they would be evaluated lazily).
- Batch: flips whose cones are disjoint can be checked together in 64-lane words
  (bit-parallel; noted in the SIMD report as the only data-parallel option here).
  Do this only if 3b shows cone propagation still dominates after the cheaper fixes.

**Constraint.** `_diversify` is a Gibbs step for the uniform distribution. Any change
must keep the sequential accept/reject semantics (each flip checked against the running
model). Run `tests/unit/dist_harness.py` and the sampling-uniformity tests before and
after; the sample distribution for a fixed seed should be identical unless the change
is intended.

**Target.** `_diversify` share from 37% to under 10% of the Verilator run.

Log: done 2026-10-17.
- **3a: the routing is intended.** Per-bench replay with `DV_LOG` shows one bench on
  bitblast: `crc_filter`, 1282 of its 1287 check-sats as `cdcl-slow`. The shape router
  measured CDCL as more than 2× slower than bitblast on this shape. The other ten benches
  are all CDCL.
- `crc_filter` was 5.26 s of the 7.3 s run. Each randomize is a fresh bitblast
  `check`: the Verilator XOR-hash asserts change the problem fingerprint, so the
  identity cache never hits.
- **3b: the split.** Setup is ~2 µs and the flip loop ~3.2 ms per call. The AIG has
  ~210 nodes and only 8 distinct inputs (the 8 bits of `m`). But the problem has ~1800
  builder vars, whose bits are constants (31k candidates per call) or aliases of `m`'s
  bits (22.8k). Each alias has its own seeded target, so each input bit was visited
  ~2800 times per call: 27k attempted flips and 573k cone-heap pops per call.
- **3c: the lever.**
  - Constant bits are no longer candidates. Readback takes a constant from the
    literal, never from `nv[1]`, so this changes nothing.
  - When the candidates cover k ≤ 16 distinct inputs and 2^k ≤ visits/4, the loop
    memoizes per input assignment whether every assertion holds. A flip is kept
    exactly when the flipped assignment satisfies, and that depends only on the k
    inputs (no other input changes in the loop). So the accept/reject sequence, and
    the sample, is the same as the cone-propagating loop's.
  - A memo miss is one full AIG pass. The memo checks the starting model and falls back
    to the plain loop if it does not satisfy.
  - `DV_DIVERSIFY_MEMO=0` runs the plain loop. `tests/unit/test_diversify_memo.py`
    checks that the two give identical output on a crc_filter session.
- Result: the full transcript's stdout is byte-identical before and after (md5 over
  40933 lines), with the memo on and off. crc_filter 4.68 → 1.45 s. vlt 7.385 →
  4.159 s (median of 5).
- Not done: setup caching, a bucketed worklist and 64-lane batching. The profile no
  longer points at them.

## Item 4: dynamic-loader startup (20% of the easy band)

**Problem.** `dv-solve-smt2` links `dv_solve_static`, so its own code needs no symbol
lookup. The loader time is `do_lookup_x`/`_dl_lookup_symbol_x`/`_dl_relocate_object`
resolving `libstdc++.so.6` (cadical is C++) and libc symbols at start.

**Scope.** This only affects one process per solve: the CLI one-shot use and the
benchmark sweeps. Python bindings and the Verilator interactive session pay it once. So
the gain is in the easy band and competition-style timing, not the Verilator loop.

**Fix options.**
1. Measure with `LD_DEBUG=statistics` to get the relocation count and time per library.
2. Link the CLI with `-static-libstdc++ -static-libgcc`. Check wheel size, the
   auditwheel policy, and the MSVC/macOS branches in `CMakeLists.txt` (~:620).
3. `-Wl,-O1 -Wl,--hash-style=gnu -Wl,--as-needed`, and `-fvisibility=hidden` on the
   static library so unused exported symbols don't need to be bound.
4. If lazy binding is on, compare with `-z now` (eager can be faster when most
   symbols are used, slower otherwise; measure).

**Target.** Loader share from 20% to under 5% of the easy band, about 15% wall time on
the band.

Log: done 2026-10-17. Gate: ctest, full pytest (no new failures).
- Measured: `LD_DEBUG=statistics` gives ~260k cycles of startup in the loader and 1962
  symbol relocations, mostly for `libstdc++.so.6`. 500 runs of a trivial solve cost
  ~0.55 ms per process against 0.16 ms for `/bin/true`. `LD_BIND_NOW` made no
  difference; `-no-pie` alone was slower.
- Fix: the CLI links `-static-libstdc++ -static-libgcc` (GNU on Linux only, option
  `DVS_STATIC_LIBSTDCXX`, behind a link check with a program that throws). Startup
  in the loader falls to ~135k cycles.
- It first failed to link: "relocation R_X86_64_PC32 against undefined hidden symbol
  `DW.ref.__gxx_personality_v0` can not be used when making a PIE object". The cause
  was `cmake/cadical.cmake`: its `objcopy -w --keep-global-symbol=ccadical_*` localizes
  every other global, including cadical's weak hidden `DW.ref.*` personality pointers,
  which the static libstdc++ objects reference.
  - Keeping `DW.ref.*` global fixes it. They are hidden, so `libdv_solve.so`'s
    exported symbols are unchanged (diffed), and every copy holds the same pointer.
  - The CLI stays a PIE.
- Result: easy band 8.7G → 7.2G user cycles (−17.5%). The CLI no longer needs
  `libstdc++.so.6` (`ldd`: libm, libc). Binary 2.55 → 2.69 MB before strip.
- Not checked here: the manylinux wheel build (auditwheel) and macOS/MSVC, which the
  option skips.

## Item 5: `trail_backtrack` cleared ENTAILED by walking every watcher chain

- Finding: ot_aon_wkup spent 27% in `trail_backtrack`. After undoing the trail it walked
  every variable's watcher chain to clear `PROP_FLAG_ENTAILED`, so each backtrack cost
  O(all watches) however little it undid. The enumeration sampler backtracks once per
  node, ~1100 nodes per check-sat.
- Change: an entailment is recorded (`trail_mark_entailed`) as an `EntailEntry` on the
  dynamic stack, newest first, beside the trail entries. `LevelMark` and
  `CheckpointMark` save `entail_top` wherever they save `trail_top` (push, seal,
  checkpoint, restore, reset in scope, full reset). A backtrack clears the flag on the
  entries newer than the mark, before popping the stack. An entailment found before the
  mark rests on bounds the backtrack keeps. The `prop_refs[prop_id] != ref` exception
  for dead post-checkpoint propagators is kept. If the stack is full the flag is left
  clear, so the propagator fires again (slower, still sound).
- Not a trail-entry kind: several conflict-analysis walkers in `dvs_lcg.c` read every
  trail entry without filtering on kind.
- Equivalence: a truly entailed propagator changes no domain when it fires, so output
  must not change. Old (19c8eb5) and new outputs are byte-identical on the whole
  Verilator transcript (md5 `8f5904ac`, same as the item 3 reference) and on all 217
  easy-band fixtures. ctest 31/31 in release and in the ASan build. All 11 Verilator
  bench transcripts are clean under the ASan CLI.
- Result (`instructions:u`): ot_aon_wkup 39.6G → 32.9G (−17%), `trail_backtrack` 27% →
  9% of its profile. Whole transcript 104.0G → 96.8G (−7%). Easy band, a57 and a67 are
  unchanged within noise.
- Side finding: Debug and Release builds draw different Verilator samples from the same
  transcript (range_1000 diverges at line 1671), deterministically, at 19c8eb5 as well.
  Debug and ASan agree. Not caused by item 5. It may be float or UB-sensitive code, so it
  is worth a look on its own.
- Log: gates passed. FUZZ_N=2000 fuzzer 4001 passed. Whole pytest: the same 28
  failures as the item 0 baseline list, none new.
