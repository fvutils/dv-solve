# Randomizing through DPI

A SystemVerilog testbench can call dv-solve directly through DPI, on any
simulator. You describe the constraints with the Python builder, embed the
compiled description in a SystemVerilog package, and solve it from
SystemVerilog as often as you like.

This route suits constraints that are generated by a tool, or that you want
solved the same way on every simulator. To randomize ordinary SystemVerilog
classes in Verilator, use dv-solve as Verilator's solver instead (see
{doc}`verilator`); nothing in your testbench changes.

The packages and functions used here are described in
{doc}`../reference/sv-api`.

## 1. Describe the problem in Python

This script builds the constraints for a bus packet, the same ones as the
class in {doc}`../getting-started/quickstart-verilator`, and writes them out
as a SystemVerilog package:

```{literalinclude} ../../examples/sv-dpi/packet_problem.py
:language: python
```

```bash
python3 packet_problem.py        # writes packet_problem_pkg.sv
```

The package holds the problem as a base64 string, plus the variable ids so
the SystemVerilog side can refer to them by name.

The string is a memory image of the problem, not a stable file format.
Generate it with the dv-solve version the simulation will load, and generate
it again after upgrading dv-solve.

## 2. Randomize from SystemVerilog

A subclass of `dvs_randomizer` returns the problem string and copies each
solution into an object. The handle functions of `dvs_dpi_pkg` give finer
control: here they pin `kind` to 7 for a few solves.

```{literalinclude} ../../examples/sv-dpi/packet_dpi.sv
:language: systemverilog
```

The packet class has no `rand` fields and no constraints: the constraints
live in the problem, and the variable ids connect the two.

## 3. Build and run

Compile `dvs_dpi_pkg.sv`, `dvs_randomizer_pkg.sv`, the generated package and
your testbench, and load the DPI library. The `dv_solve` Python package tells
you where these are (see {doc}`packaging`). With Verilator:

```bash
SV=$(python3 -c 'import dv_solve; print(dv_solve.get_svdirs()[0])')
DPI=$(python3 -c 'import dv_solve; print(dv_solve.get_dpi_lib())')

verilator --binary --top-module top -o packet \
    $SV/dvs_dpi_pkg.sv $SV/dvs_randomizer_pkg.sv \
    packet_problem_pkg.sv packet_dpi.sv \
    $DPI -LDFLAGS "-Wl,-rpath,$(dirname $DPI)"
./obj_dir/packet
```

Other simulators load the library with their usual option for DPI
libraries, such as `-sv_lib`.

The run prints something like:

```text
addr=0000091c len=4 kind=8
addr=00000f04 len=10 kind=10
addr=00000088 len=13 kind=7
addr=00000a44 len=9 kind=10
addr=00000b40 len=6 kind=2
pinned: len=13
pinned: len=10
pinned: len=11
```

## How solving behaves

- **Compile once, solve many times.** The problem is compiled when the
  handle is created; each solve reuses it, so a solve costs only the search.
- **Every solve starts fresh.** A solve starts from the constraints and the
  active pins, never from the previous solution, so successive calls give
  different solutions.
- **Seeds.** Passing `$urandom()` as the seed makes the results follow the
  simulator's seed. A seed of 0 continues from the handle's own random
  state.
- **Pins and checkpoints.** A pin fixes a variable for every following
  solve. Take a checkpoint before pinning, and restore it to remove the
  pins again; a checkpoint can be restored any number of times.

## When something goes wrong

`dvs_dpi_compile_b64` returns `null`
: The string is malformed (for example, cut short when it was pasted), or
  compiling showed the problem has no solution. `dvs_randomizer` stops the
  simulation with `$fatal` in this case.

`dvs_dpi_solve_h` returns 1
: No solution exists under the current pins.

`dvs_dpi_solve_h` returns 3
: Some constraint could not be compiled, and the solution found breaks it.
  `dvs_dpi_n_uncompiled_h` says how many constraints were affected. The
  solution is not applied.
